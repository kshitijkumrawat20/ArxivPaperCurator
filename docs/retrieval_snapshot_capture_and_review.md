# Frozen ranking capture and human review (Phase 4D)

Phase 4D adds explicit, manually invoked tools around the Phase 4C evaluator.
They do not run during application startup, tests, ingestion, or Airflow. The
capture client is not run against any service as part of this change.

## 1. Validate query payloads locally

The capture tool maps each `queries.json` case to the current API contract:

- `project_match` → `POST /api/v1/papers/match-project`.
- `research_radar` → `POST /api/v1/papers/radar` (final fused feed only).

Project Match copies the project description and supported optional query fields;
`expected_filters.categories`, `date_from`, and `date_to` are passed as request
filters. Radar copies topics, lookback, and bounded result limits, and passes
categories. The Radar API has no explicit date-bound fields; non-null Radar
`date_from`/`date_to` filters are rejected instead of silently omitted. Defaults
are made explicit in the built request: `top_k=10`, Radar lookback 30 days, and
per-topic candidate limit 20. The actual API schemas remain authoritative.

`--validate-only` checks case selection, URLs, constraints, and payload
construction, prints those payloads, and makes no request or output file. The API
base URL must be explicitly supplied; credentials, query strings, and fragments
are rejected. The manifest stores only the origin, not the deployment path.

Illustrative local validation command (not executed against a service):

```powershell
python tools/capture_retrieval_snapshots.py `
  --queries benchmarks/ai_ml_research_v1/queries.json `
  --api-base-url https://your-chosen-api.example `
  --snapshots-out captures/run-2026-10-22/rankings.json `
  --manifest-out captures/run-2026-10-22/manifest.json `
  --validate-only
```

An explicit capture command, to be run by an operator in a chosen environment
outside this development task, omits `--validate-only`:

```powershell
python tools/capture_retrieval_snapshots.py `
  --queries benchmarks/ai_ml_research_v1/queries.json `
  --api-base-url https://your-chosen-api.example `
  --snapshots-out captures/run-2026-10-22/rankings.json `
  --manifest-out captures/run-2026-10-22/manifest.json `
  --timeout-seconds 10 --retries 0
```

Capture defaults to no retry; at most one retry may be explicitly enabled. Only
transient timeout, connection, 429, and selected 5xx failures are retryable.
Existing output paths are refused unless `--overwrite` is explicit. `--case-id`
can select a subset; selected-case output contains only those runs, so use a new
snapshot name when recapturing one case to avoid losing a prior complete run.

## 2. Snapshot and manifest artifacts

The ranked snapshot uses Phase 4C's `format_version: "1.0"` schema and includes
matching benchmark ID/version, one ranking run per successful case, target,
method, exact arXiv ID, rank, and optional original score. Project Match stores
its BM25 `search_score`; Radar stores its RRF `fusion_score`. These are
provenance only, not relevance probabilities. Distinct arXiv versions remain
distinct. Duplicate exact IDs or ranks in one API response make that case fail;
they are never silently merged.

The separate manifest records the UTC capture timestamp, sanitized API origin,
per-case endpoint path, HTTP status when known, attempts, sanitized error
category, result count, and bounded metadata needed for review (title, abstract,
authors, categories, date, source URL). The current endpoints do not expose a
metadata-index snapshot identifier, so the manifest records `null` and explains
that capture time does **not** freeze the underlying index. HTTP bodies, tokens,
credentials, and raw exception text are not written to the manifest. Failed
requests appear in the manifest and have no successful ranking row; they are not
converted into valid empty results. A successful response with an empty paper
list is a valid empty ranking.

## 3. Human-review packet and annotation

After inspecting the manifest for failures, build a packet from successful
cases. The packet keeps source metadata under each `paper` record; the separate
annotation template contains only exact IDs and editable review fields. All
generated annotations start `unjudged` with null grades and empty rationales.
No relevance, rationale, or reviewer identity is generated by the tool.

```powershell
python tools/prepare_relevance_review.py packet `
  --queries benchmarks/ai_ml_research_v1/queries.json `
  --snapshots captures/run-2026-10-22/rankings.json `
  --manifest captures/run-2026-10-22/manifest.json `
  --packet-out captures/run-2026-10-22/review-packet.json `
  --annotations-out captures/run-2026-10-22/annotations.json
```

Reviewers set each paper's status to `judged`, assign a grade, and provide a
short rationale. Optional `reviewer_id` and ISO `annotated_at` fields are
available. Judge against the complete project description or research topic,
not just shared keywords or the rank. Use this scale consistently:

- `0`: Not relevant to the stated query.
- `1`: Marginally relevant.
- `2`: Relevant.
- `3`: Highly relevant.

Validate the edited annotations and convert them to Phase 4C's evaluator input:

```powershell
python tools/prepare_relevance_review.py to-judgments `
  --packet captures/run-2026-10-22/review-packet.json `
  --annotations captures/run-2026-10-22/annotations.json `
  --judgments-out captures/run-2026-10-22/judgments.json
```

The converter rejects changed/duplicate IDs, out-of-range grades, missing
rationales, malformed dates, missing packet cases, and annotation/packet version
mismatches. It preserves optional reviewer IDs and dates as annotation
provenance. If some papers are still unjudged, only human-judged records are
written to the evaluator judgments; absent labels remain unjudged under Phase
4C's explicit metric convention. A target with no judged papers stays explicitly
`unjudged`.

Then run the Phase 4C evaluator on the frozen query file, converted judgments,
and captured rankings. Keep those inputs and both reports together. Example
(illustrative only; not executed against a live API):

```powershell
python tools/retrieval_eval.py `
  --queries benchmarks/ai_ml_research_v1/queries.json `
  --judgments captures/run-2026-10-22/judgments.json `
  --rankings captures/run-2026-10-22/rankings.json `
  --json-out captures/run-2026-10-22/evaluation.json `
  --markdown-out captures/run-2026-10-22/evaluation.md
```

Radar capture currently supports only the final fused feed; this workflow does
not claim topic-level ranking evaluation because the API response does not
expose those underlying per-topic lists.

Each capture is an observation at a point in time, not a reproducible copy of
the index state. For fair later comparisons, preserve the benchmark version,
rankings, manifest, judgments, evaluator version, and reports; record any
available environment/index identifiers separately when an operator can verify
them.
